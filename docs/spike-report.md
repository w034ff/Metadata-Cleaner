# 事前検証（スパイク）報告

要件定義書 §8 の事項を、小さなプログラムで確かめた結果をまとめる。検証用のコードは `spike/strip-bench` にある。

- 画像の試験用ファイルは、PDF Converter のスパイクの画像（`color.jpg`、`cmyk.jpg`、`alpha.png`、`alpha.webp`）に、架空のメタデータを足して作った。位置情報は架空の値（北緯 12 度 34 分、東経 65 度 43 分）、名前は `Spike Author` などの仮のものにした。
- PDF は、PDF Converter のスパイクで使った第三者の PDF 15 個（pdf.js のテスト用の PDF ほか）を使った。第三者のものなので、リポジトリには含めない。
- 実施日: 2026-10-09
- 環境: WSL2（Ubuntu）、x64。Windows での確認は、実装の最初のタスクで行う。

## 1. 結論

| 事項 | 決定 |
| --- | --- |
| 画像（JPEG / PNG / WebP）の除去 | **自前で書く**。セグメントとチャンクを読み、残すものだけを書き直す。img-parts は使わない（§2.1） |
| EXIF の読み取り（種類の分類と向き） | **kamadak-exif** 0.6.1（BSD-2-Clause） |
| PDF の読み書き | **lopdf** 0.45.0（MIT）。オブジェクトストリームを使って書き直す（`save_modern`） |
| pdfium | **アプリには同梱しない**。描画が元と同じかを確かめるテストでだけ使う |
| 別のプロセス | **PDF の処理は別のプロセスで動かす**。画像は同じプロセスで扱う（§4） |

純 Rust だけで済み、OS ごとのネイティブのライブラリを同梱しなくてよい。

## 2. 画像

### 2.1 img-parts を使わない理由

img-parts 0.4.0 は、JPEG の最初のスキャン（SOS）より後ろを、すべて圧縮データとして扱う。そのため、次のものを見落とし、書き出したファイルにもそのまま残す。

- EOI より後ろに付いたデータ（モーションフォトの動画、MPF の 2 枚目以降の画像など。これらは自分の EXIF を持ちうる）
- プログレッシブの JPEG で、スキャンとスキャンの間にあるセグメント

自前の読み取り（`spike/strip-bench/src/jpeg.rs`）は、すべてのスキャンを読んで EOI で止まる。PNG と WebP も、それぞれ 100 行ほどで書ける（IEND の後ろ、RIFF の大きさの後ろは捨てる）。いずれも小さいので、自前で書いて全部をテストする。

### 2.2 結果

| 入力 | 元にあったもの | 書き出したあと | 画像のデータ | 画素 | 向き |
| --- | --- | --- | --- | --- | --- |
| JPEG（RGB、向き 1） | EXIF（位置・日時・機器・メーカーノート・シリアル番号・ソフト・作者・著作権・サムネイル）、XMP、ICC、MPF、Photoshop/IPTC、コメント、EOI の後ろ 46 バイト | ICC だけ | 同じバイト列 | 同じ | 同じ |
| JPEG（RGB、向き 6） | 同上 | ICC と、向きだけの EXIF | 同じバイト列 | 同じ | 90 度回転のまま |
| JPEG（CMYK、Adobe APP14 付き） | 同上 | ICC と Adobe APP14 | 同じバイト列 | 同じ | 同じ |
| PNG（透過、`eXIf` の向き 6） | `tEXt`（IDAT の前と後ろ）、XMP の `iTXt`、`eXIf`、`tIME`、IEND の後ろ 13 バイト | 向きだけの `eXIf` | 同じ | 同じ | 90 度回転のまま |
| WebP（可逆、透過、EXIF の向き 3） | EXIF、XMP | 向きだけの EXIF（VP8X の XMP のフラグも下ろした） | 同じ | 同じ | 180 度回転のまま |

- 「画像のデータ」は、JPEG では残すセグメント（表、フレーム、スキャン、ICC、Adobe）を、PNG では残すチャンクを、WebP では画像のチャンクを、元と書き出したあとで比べた。
- 「画素」と「向き」は image 0.25 で読んで比べた。
- 向きだけの EXIF は、IFD を 1 つ、項目を 1 つ（Orientation）だけ持つ 26 バイトの TIFF。向きが 1（回転なし）なら EXIF ごと書かない。
- JFIF（APP0）は残すが、その中のサムネイルの大きさを 0 にする。JFXX（APP0 の拡張のサムネイル）は消す。
- MPF（APP2）は、EOI の後ろの画像を消すと位置が合わなくなるので、一緒に消す。
- C2PA などの来歴の情報（JPEG の APP11、PNG の `caBX`）は、「残すもの以外は消す」規則で自然に消える。

### 2.3 速さ

4000 × 3000 ピクセル（約 2.5 MB）の JPEG で、除去が 3.6 ms、書き出したあとの確認が 2.7 ms だった。要件（NFR-02）の 0.5 秒に対して十分に速い。

## 3. PDF

### 3.1 消したもの

lopdf で読み、次を消してから、残ったオブジェクトだけでファイル全体を書き直した。

- トレーラーの `/Info`（文書情報）と `/ID`
- すべての辞書（入れ子の中も含む）の `/Metadata`（XMP）、`/PieceInfo`（Illustrator などが書く私的なデータ）、`/Thumb`（ページのサムネイル）
- フィルターが `DCTDecode` だけの画像のストリームの中の JPEG にある EXIF・XMP など（§2 と同じ処理。PDF では向きの情報を使わないので、向きも残さない）
- どこからも参照されなくなったオブジェクト（`prune_objects`）

`/Thumb` は最初は対象にしていなかった。`cmykjpeg.pdf` で残っているのを見つけて加えた。ページのサムネイルは、編集する前の内容を写していることがある。

### 3.2 過去の版

試験用の PDF に、作成者を `Spike Author` から `Spike Editor` に変える版を追記保存で足した。元のファイルには両方の名前がバイト列として残る。書き直したあとは、どちらも残らなかった。lopdf は最新の版のオブジェクトだけを持ち、全体を書き直すためである。

### 3.3 結果

- 試験用の PDF（TAMReview.pdf と shared-mime-info-spec.pdf をもとに、上のメタデータをすべて足したもの）: 書き出したあと、消す対象は何も残らなかった。生のバイト列を `Spike` などで探したほか、展開したストリームの中も探した。全ページの描画が、元と画素単位で一致した（23 ページ、19 ページ）。
- 第三者の PDF 15 個: 暗号化された 1 個は「暗号化」として断った（制限だけを掛けたものも lopdf は空のパスワードで開くので、`was_encrypted` で見分ける）。残りの 14 個はすべて、消す対象が残らず、全ページの描画が元と一致した。処理は 1 個あたり 4 ms 以下だった。
- 大きさ: オブジェクトストリームを使わずに書くと、元がオブジェクトストリームを使っていた PDF が 27% 大きくなった（shared-mime-info-spec.pdf、148 KB → 187 KB）。`save_modern` で書くと 15 個のうち 14 個が小さくなり、残りの 1 個も 1.3% の増加で済んだ。

### 3.4 電子署名

署名の辞書（`/Type /Sig` または `/FT /Sig`）があれば断るようにした。手元に署名付きの PDF がないので、まだ確かめていない。T02 で試験用の PDF を作るときに確かめる。

## 4. 壊れたファイルと別のプロセス

- 15 個の PDF それぞれを、途中で切ったもの（10%、50%、90%）と、一部のバイトを書き換えたもの（20 通り）にして、計 368 個を処理した。1 個ずつ子のプロセスで動かし、10 秒で打ち切った。成功が 241 個、エラーが 127 個で、異常終了と時間切れは 0 件だった。
- 配列を 1000 段、1 万段、10 万段に入れ子にした PDF も、落ちずに処理できた。
- それでも、PDF の処理は別のプロセスで動かす。理由は次のとおり。
  - lopdf は大きな構文解析器で、この程度の試しでは、異常な入力でメモリを使い切ったりスタックがあふれたりしないとは言い切れない。どちらも `catch_unwind` では捕まえられず、アプリごと終了する（NFR-01 に反する）。
  - PDF Converter のワーカーの設計（同じ実行ファイルを別の引数で起動し、時間とメモリの上限を掛ける）を、ほぼそのまま使える。起動の負担は 10 ms 未満で済む（PDF Converter のスパイク §3）。
- 画像は同じプロセスで扱う。自前の読み取りは、ファイル全体を読んだ後に位置を進めるだけで、再帰も大きな割り当てもない。上限の確認と、壊れたファイルのテストで十分に守れる。

## 5. ExifTool での照合

本アプリとは別の実装で「残っていない」ことを確かめるため（NFR-03）、ExifTool 12.76（Ubuntu の `libimage-exiftool-perl`）で、試験用ファイルと書き出したファイルを読み比べた。

- 画像: 試験用ファイルからは、ExifTool も位置情報、機種、シリアル番号、メーカーノート、日時、作者、著作権、ソフト、サムネイル、PNG のテキストを読み出した。書き出したファイルで ExifTool が読み出したのは、向き（向きが 1 でないものだけ）、JFIF、Adobe APP14 だけだった。
- PDF: 試験用の PDF からは文書情報（作成者、表題、作成ソフト、PDF 作成ソフト、作成日時）と XMP を読み出し、書き出したものからは何も読み出さなかった。第三者の PDF 15 個（暗号化された 1 個を除く）も、文書情報と XMP の項目が 0 個になった（元は 0〜49 個）。
- ExifTool では確かめられないもの: PDF の中の JPEG の EXIF（`-ee` を付けても読まない）と、追記保存の過去の版（最新の版の文書情報だけを読む）。この 2 つは、自前の読み取りと生のバイト列の検索で確かめる（§3.2、§3.3）。
- 試験用ファイルの作りの不備で、ExifTool が読めなかったもの: 偽の ICC（「長さが不正」の警告）、RDF の形をしていない XMP（PNG と WebP）、IPTC。どれも本アプリの除去の問題ではないが、本番の試験用ファイルは ExifTool が読める正しい形で作る（§6）。

## 6. 詳細設計で決める事項（検証で見つかったもの）

- 残す項目の正確な一覧。スパイクでは次を残した。
  - JPEG: JFIF（サムネイルを除く）、ICC、Adobe APP14、向きだけの EXIF
  - PNG: `IHDR` `PLTE` `IDAT` `IEND` `tRNS` `gAMA` `cHRM` `sRGB` `iCCP` `cICP` `mDCV` `cLLI` `sBIT` `bKGD` `acTL` `fcTL` `fdAT`、向きだけの `eXIf`
  - WebP: `VP8 ` `VP8L` `VP8X` `ALPH` `ANIM` `ANMF` `ICCP`、向きだけの EXIF
- 解像度（dpi）。EXIF にだけ解像度がある JPEG では、EXIF を消すと解像度も消える。`XResolution` `YResolution` `ResolutionUnit` を向きと一緒に残すかどうか。PNG の `pHYs` を残すかどうか（スパイクでは消した）。
- PDF の `/ID`。消すか、乱数で作り直すか。
- 書き出したあとの確認で、ストリームを展開する量の上限（`decompressed_content_with_limit`）。上限がないと、圧縮爆弾でメモリを使い切る。
- PDF の中の、フィルターが `DCTDecode` だけではない JPEG（`FlateDecode` との組み合わせなど）と、JPEG 2000（`JPXDecode`。XMP を持ちうる）の扱い。
- 試験用ファイル。第三者の PDF は使えないので、PDF Converter の `gen_fixtures` のように、架空のメタデータを持つ画像と PDF をコードで作る。ICC、XMP、IPTC は ExifTool が読める正しい形にする（§5）。プログレッシブの JPEG（スキャンの間のセグメント）、署名付きの PDF、`/Thumb` を持つ PDF も作る。image ではプログレッシブの JPEG を書けないので、作り方を決める。
- ICC の説明文。利用者の名前などを含みうるが、残す（見た目を保つほうを優先する）かどうか。
