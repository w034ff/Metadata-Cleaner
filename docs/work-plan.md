# 作業計画

[requirements.md](requirements.md)（要件）と [design.md](design.md)（設計）を実装するためのタスク分割と進め方。進め方は PDF Converter と同じにし、そこで分かったこと（Windows での確認を早めに行う、依存の検査を最初から入れる、PR の前に手元でレビューする、大文字小文字だけが違うファイル名は Windows で壊れる）を取り入れている。

## 1. 役割

| 役割 | 担当 | 責務 |
| --- | --- | --- |
| 設計・レビュー | Opus 5.5 | 要件定義・設計・作業計画の作成と更新、タスクごとのレビュー、検証結果の設計への反映 |
| 実装・テスト | Sonnet 5.5 または Gemini（agy） | タスクの実装とテスト、報告、レビュー指摘への対応。どちらに渡すかはタスクごとにオーナーが決める |
| オーナー | 利用者 | 判断が必要な事項の決定、GitHub リポジトリの作成、Windows 実機での確認、push と PR の作成、マージ |

- `docs/requirements.md` と `docs/design.md` を更新するのは設計担当だけ。実装担当は設計どおりに作れない、または設計が曖昧な場合、実装を止めて報告の「設計への質問」に書く。
- 実装担当の規約は [GEMINI.md](../GEMINI.md)（T00 で PDF Converter のものを元に作る）。Sonnet に渡すときも、このファイルを読ませる。
- リポジトリはオーナーが GitHub に作る（公開、名前は `Metadata-Cleaner`）。Settings → Advanced Security で **Secret scanning** と **Push protection**、**Dependabot alerts** と **Dependabot security updates** を有効にする。main には PDF Converter と同じルールセット（PR 必須、`Test (ubuntu-latest)` と `Test (windows-latest)` の成功が必須、ブランチが最新であること）を掛ける。
- 実装担当の環境では、新しい crate や npm パッケージを取得できないことがある。design.md §2 で決めた依存は T00 で設計担当がまとめて入れる。後から依存が要るとわかったら、設計担当が小さな PR で先に入れる。
- T00、T01 と T16 の `release.yml` は設計担当（Opus）が実装する。ひな形の作成、`npm install`、CI の権限の設計を含むため。レビューと報告の書式は実装担当のタスクと同じにする（§2）。

## 2. 1 タスクの流れ

PDF Converter の work-plan §2 と同じ。要点:

1. オーナーが実装担当にタスク ID を渡す（例: 「docs/work-plan.md の T03 を実装して」）。
2. 実装担当は `main` から `task/T03-<短い名前>` ブランチを作り、実装とテストを行う。コミットのたびに pre-commit フック（§2.3）が検査を走らせる。
3. §5 の共通の完了条件をすべて満たしたら、§2.1 の書式で報告を `pr-description.md`（リポジトリの直下、git の管理外）に書き、最後に §2.4 の合図 `agent-status.json` を書く。PR は作らない。§2.2 の条件に当たったら、状態を「中断」にして止める。
4. Opus がブランチの差分（`git diff main...<ブランチ>`）を §6 の観点でレビューする。指摘は作業ツリーの直下の `agent-review.md`（git の管理外）に書く。実装担当は同じブランチで直してコミットし、`pr-description.md` を今の状態に合わせて書き直し、`agent-status.json` を `fixed` にする。
5. 合格したら、Opus が `pr-description.md` の末尾に §2.1 の「手元のレビュー」の節を足したものを作業ツリーの外（`~/metadata-cleaner/pr-bodies/`）に作り、`agent-review.md` を消して、push と PR の作成のコマンドをオーナーに渡す。push と PR の作成はオーナーが行う（公開リポジトリに出る前に人が見る関門として、Claude Code の設定で `git push` を禁止している）。CI（Ubuntu と Windows）が通ったら、オーナーがマージする（Create a merge commit）。CI の失敗を実装担当に直させるときも、`agent-review.md` で渡す。

差し戻しは PR の前に手元で済ませ、PR は CI とルールセット（両 OS のテスト、依存の検査）を通す最後の関門にする。

1 つの PR に 1 つのタスクだけを含める。タスクの範囲外の変更（ついでのリファクタリング、依存の更新など）は含めない。

### 2.1 報告の書式

PR の説明（`pr-description.md`）は日本語で、次の節をこの順にすべて書く。当てはまるものがない節も消さずに「なし」と書く（書き忘れと区別するため）。会話の最後の返答には、報告の中身を繰り返さず、状態（完了 / 中断）だけを書く。

```markdown
# T03 画像の読み書き

- 状態: 完了 / 中断
- ブランチ: `task/T03-image-formats`

## 完了条件の満たし方

work-plan.md の完了条件ごとに、どのテスト・確認で満たしたか。

## 実行したコマンドと結果

実際に実行したものだけを書く。§5 のコマンドと、完了条件が求めた計測値（所要時間など）。

## 設計との差異

差異と、その理由。

## 見つけたが直していない不具合

タスクの範囲外で見つけたもの。

## オーナーに確認してほしい操作

Windows での確認、見た目の確認など、自動化できないもの。操作と、期待する結果を箇条書きで。

## 設計への質問

中断のときは、§2.2 のどの条件に当たったか、試したこと、最後に出たエラーの要点。
```

- 根拠として挙げるファイル、設定、設計の記述は、実在して、その内容が書いてあるものだけにする。
- PR の本文を作るとき、Opus が末尾に次の節を足す（実装担当は書かない）。差し戻しがなくても「差し戻し: なし」と書く。各回は指摘の要点と、直したコミット。

  ```markdown
  ## 手元のレビュー

  - 差し戻し: 1 回
  - 1 回目: 指摘の要点 → `abc1234`
  - レビュー担当が直したもの: なし
  ```

### 2.2 設計担当に相談する条件

次のどれかに当たったら、実装を止め、報告の「状態」を「中断」、「設計への質問」に理由を書いて知らせる。自分の判断で押し切らない。

- design.md の決定（プロセスの分け方、ワーカーの役割、パスを渡さない IPC、消すものと残すもの、上限の値など）に反する変更が必要に見えた。
- 依存の追加・更新、Rust の版（`rust-toolchain.toml`）の変更、ツールの導入、ネットワークへの接続が必要になった。または、必要なコマンドが権限の設定で拒否された。
- work-plan.md・design.md と、実際のコードやライブラリの API が食い違っている。
- 同じ失敗（コンパイル、テスト、clippy、pre-commit フック）を 3 回直そうとして解決しない。
- セキュリティの境界に関わる変更が必要になった（パスを受け取るコマンド、capabilities の権限、CSP、メインプロセスで PDF を読む処理、ファイルの中身から作った文字列をログに書く処理）。

### 2.3 pre-commit フック

- `.githooks/pre-commit` が、§5 のローカルの検査を走らせ、1 つでも失敗したらコミットを止める。人間のコミットも同じ検査を通る。
- フックを有効にする `git config core.hooksPath .githooks` は、オーナーが T00 のあとに一度だけ実行する。同じリポジトリの作業ツリー（`task`、`chore`、`opus`）は、この設定を共有する。実装担当は git の設定を変えない。
- `--no-verify` などでフックを迂回しない。フックが通らない状態ではコミットできないので、中断するときの報告はコミットせずに `pr-description.md` に置く。
- 文書だけのコミットも検査が走る。時間がかかっても迂回しない。

### 2.4 完了の合図（`agent-status.json`）

PDF Converter の work-plan §2.4 と同じ。報告を書き終えたら、最後の手順として、作業ツリーの直下に `{ "task": "T03", "state": "done" }` の形で書く。`state` は `done`（完了、すべてコミット済み）、`blocked`（§2.2 による中断）、`fixed`（差し戻しを直した、すべてコミット済み）のどれか。`agent-status.json` は実装担当だけが書き、`agent-review.md` は設計担当だけが書く。

## 4. 各タスクの内容と完了条件

### T00 リポジトリと開発基盤の初期化

内容:
- Tauri 2 + React + TypeScript + Vite のプロジェクトを作り、design.md §3 のディレクトリ構成にする。Cargo ワークスペースに `crates/core`、`crates/worker`、`src-tauri` を含める。アプリの識別子とウィンドウの大きさ（既定 1200×800、最小 960×640）を設定する。
- design.md §2 の依存をすべて入れる（`kamadak-exif`、`lopdf`（`default-features = false`、`crates/worker` だけ）、`tempfile`、`ts-rs`、`tauri-plugin-dialog`。dev-dependencies に `hayro`、`image`、`jpeg-encoder`）。後のタスクで実装担当が依存を足さずに済むようにするため。
- `GEMINI.md` を PDF Converter のものを元に作る。参照する文書とモックアップの名前、セキュリティの境界（§2.2）を、このアプリに合わせる。
- `.githooks/pre-commit`（§2.3）、ESLint と Prettier、`rustfmt`、`clippy`（`-D warnings`）の設定、`rust-toolchain.toml` は PDF Converter と同じにする。
- `.github/workflows/ci.yml`: Windows と Ubuntu で fmt、clippy、`cargo test`、lint、型検査、フロントエンドのテストを回す。ジョブの名前は `Test (ubuntu-latest)` と `Test (windows-latest)`。
- `LICENSE`（MIT）。`.gitignore` は PDF Converter と同じ内容から pdfium の行を除き、`spike/` の生成物を加える。
- 既存の `spike/` は残す（スパイクの記録）。ワークスペースには含めない。

完了条件:
- WSL（WSLg）で `npm run tauri dev` を実行すると空のウィンドウが開く。
- CI が両 OS で成功する。
- `any`、型アサーション、`class` を含むファイルを試しに作ると lint が失敗し、整形の崩れたファイルや失敗するテストを試しに入れるとフックがコミットを止めることを確かめ、報告に書く（確認用の変更はコミットしない）。

### T01 ワーカーの起動とメモリの上限（両 OS で確認）

内容:
- `src-tauri/src/main.rs` の `--pdf-worker` の分岐と、PDF Converter の `crates/worker` から写したメッセージの枠組み（長さ + JSON のヘッダー + 本体）。要求は版を返す `Ping` の 1 つだけ（本格的な要求は T07）。
- メモリの上限（design.md §5.3）: Linux の `setrlimit`、Windows のジョブオブジェクト（`windows_job.rs` を写す）。
- CI と、`tauri build` を試すための一時的なワークフロー（`workflow_dispatch`）で、4 種類のインストーラーを作る。

完了条件:
- 4 種類のインストーラー（MSI、NSIS、AppImage、.deb）からインストールしたアプリで、ワーカーが起動して `Ping` に答えることを確認する。Windows はオーナーが確認する。
- メモリの上限を超える確保をするテスト用の要求で、ワーカーだけが終了し、メインプロセスが続けて動くことを両 OS で確認する。
- Windows で、メインプロセスを強制終了したときにワーカーが残らないことを確認する。

### T02 フィクスチャの生成

内容:
- design.md §11.1 のフィクスチャを作る `crates/core/examples/gen_fixtures.rs` と、生成し直したものとコミット済みのものを比べる `crates/core/tests/fixtures.rs`。生成したファイルをコミットする。
- ICC の最小のプロファイル、プログレッシブの JPEG へのセグメントの差し込み、暗号化された PDF（PDF Converter の `gen_fixtures` の RC4 を写す）、署名付きの PDF、Web 表示用に最適化した PDF、追記保存の 2 つ目の版。
- ファイル名は小文字だけにする（大文字小文字だけが違う名前を作らないため）。

完了条件:
- すべてのフィクスチャがコミットされ、`gen_fixtures` を実行し直すと同じファイルができる。
- 各フィクスチャを ExifTool（`exiftool -a -G1 -s`）で読み、design.md §11.1 の「内容」のメタデータが読み出されることを確かめ、その出力の要点を報告に書く（ICC・XMP・IPTC が警告なしで読めること。スパイク §5 では偽のものが読めなかった）。ExifTool はオーナーの環境に入っている。
- `encrypted.pdf` と `restricted.pdf` を lopdf で読み、`was_encrypted()` が真になることをテストで確かめる。

### T03 画像の読み書き（JPEG・PNG・WebP）

内容: design.md §4.1〜§4.4 を `detect.rs`、`jpeg.rs`、`png.rs`、`webp.rs` に実装する。残す情報だけの EXIF（§4.5）は T04 で作るので、このタスクでは EXIF を受け取って置き換える部分を関数の引数にし、テストでは固定のバイト列を渡す。

完了条件:
- 形式の判定: 4 形式のフィクスチャ、`webp_named.jpg`、テキストのファイル（`UnsupportedFormat`）、上限を超える大きさ（`TooLarge`。大きなファイルを作らず、上限の比較を関数で確かめる）。
- 読み取り: `corrupt.*` → `DecodeFailed`。JPEG の詰め物の `FF`、プログレッシブのスキャンの間のセグメント、EOI の後ろのデータ、PNG と WebP の後ろのデータを正しく扱う。
- 除去: §4.2〜§4.4 の表の各行（残すもの、消すもの、置き換えるもの）に 1 つ以上のテスト。残すセグメントとチャンクが元のバイト列のままであること。WebP の VP8X のフラグと EXIF の位置。
- 画像のデータのバイト列（`image_segments` など）が、除去の前後で同じであること。

### T04 EXIF・XMP・IPTC の分類と詳細、画像の品質テスト

内容: design.md §4.5、§4.7 を `exif.rs`、`xmp.rs`、`iptc.rs`、`report.rs` に実装し、T03 の除去につなぐ。§11.2 の画像の品質テストと、JPEG の性能テストを作る。

完了条件:
- 残す情報だけの EXIF: 向き 1〜8、解像度のあり・なし・欠け、読めない EXIF。kamadak-exif で読み直して値が同じこと。
- 分類: §4.5 の表の各行の代表の項目に 1 つ以上のテスト。向き・解像度・ICC が数えられないこと。分類できない XMP と IPTC が `Other` になること。
- 詳細: 緯度・経度の度分秒と方角、日時の形、`MAX_DETAIL_VALUE_CHARS` と `MAX_DETAIL_ENTRIES` の打ち切り。
- 品質テスト（§11.2 の画像）: 全画像のフィクスチャで、画素・向き・ICC が同じ、除去後の分類が空。
- 性能テスト（§11.2）: 4000×3000 の JPEG で 2 秒以内（`--release`）。報告に実測値を書く。`ci.yml` に性能テストを `--release` で実行する手順を加える。

### T05 出力名

内容: design.md §6.4。PDF Converter の `naming.rs` とそのテストを写し、PDF → 画像の番号の部分（このアプリでは使わない）を除く。

完了条件: 重なりなし、既存のファイルとの重なり、入力同士の重なり、番号の繰り上がり、大文字小文字の違い、多重拡張子、拡張子のない名前、入力の並び順を変えても結果が同じ、のテスト。

### T06 PDF の調査と除去

内容: design.md §4.6 を `crates/worker/src/pdf.rs` に実装する（ワーカーの要求につなぐのは T07）。§11.2 の PDF の品質テストと性能テストを作る。

完了条件:
- 断る PDF: `encrypted.pdf`・`restricted.pdf` → `PdfEncrypted`、`signed.pdf` → `PdfSigned`、`corrupt.pdf` → `PdfOpenFailed`。
- 除去: §4.6 の「消すもの」の各項目に 1 つ以上のテスト。`DCTDecode` だけでない JPEG と、読めない JPEG のストリームがそのまま残ること。
- 調査: `full.pdf` で §4.5 の種類が期待どおり（`History` を含む）、`linearized.pdf` で `History` が出ない、XMP の展開が `MAX_XMP_BYTES` で止まる。
- 品質テスト（§11.2 の PDF）: 除去の前後で hayro の描画が画素単位で一致する、除去後の分類が空、生のバイト列にフィクスチャの架空の値が含まれない。
- 性能テスト: 100 ページの PDF の除去が 5 秒以内（`--release`）。報告に実測値を書く。

### T07 ワーカーとワーカーの管理

内容:

## 6. レビューの観点

Opus は各タスクを次の観点でレビューする。

1. **設計との一致**: design.md の該当箇所どおりか。差異がある場合、その理由は妥当か。
2. **正しさ**: 境界値、エラー経路、並行処理（ワーカーの貸し出し、時間切れ、キャンセル）の不具合がないか。
3. **消し残し**: 消すべき情報が残る経路がないか（後ろのデータ、スキャンの間、入れ子の辞書、過去の版、読めない入力のときの扱い）。確かめる処理（§6.3）を迂回して保存する経路がないか。
4. **テストの質**: 完了条件のテストが揃っているか。実装をなぞるだけで、壊しても通るテストになっていないか（機能を一時的に壊して確かめる）。
5. **セキュリティ**: パスを受け取るコマンドや新しい権限が増えていないか。通信する依存が入っていないか。メインプロセスで PDF を読んでいないか。ワーカーがファイルを書いていないか。ファイルの中身から作った文字列をログに書いていないか。公開してはならない情報（API キー、トークン、個人のファイルパスなど）が含まれていないか。
6. **規約**: GEMINI.md（型、コメント、定数、多言語、コミットメッセージ）。コミットの本文が実装の説明になっていて理由がないものも、ほかの指摘と同じく差し戻す。最後のコミットは実装担当が `git commit --amend` で直す。それより前のコミットは、PR を作る前に設計担当が書き直し、§2.1 の「レビュー担当が直したもの」に書く。
7. **ファイル名**: 大文字小文字だけが違う名前がないか（Linux のレビューでは見えないので、`git ls-files` を小文字にして重複を調べる）。
8. **範囲**: タスクの範囲外の変更が含まれていないか。
